# Експерименти

Матеріал для експериментальної частини роботи: симулятор користувачів, офлайн-метрики рекомендацій і навантажувальні тести. Скрипти — TypeScript, який Node 24 виконує напряму (без збірки).

Потрібен запущений стек (`docker compose up`) з debug-переглядом Analytics (`ANALYTICS_DEBUG_ENDPOINTS=true`, так за замовчуванням у dev). Для швидшого прогону:

```bash
FAKE_TRANSCRIPTION_DELAY_MS=0 FAKE_LLM_DELAY_MS=0 PROFILE_RECOMPUTE_INTERVAL_MS=10000 \
  docker compose up -d ai-enrichment analytics
```

## 1. Симулятор — `npm run simulate`

[`src/simulate.ts`](src/simulate.ts): через справжній API Core завантажує каталог (`SONGS=80`, назви з `@faker-js/faker` з фіксованим `SEED=2026` — фейковий аналізатор виводить теги з назви, тож теги щоразу ті самі), створює `USERS_PER_PERSONA=5` користувачів на кожну з 6 персон ([`src/personas.ts`](src/personas.ts): улюблені й нелюбі теги) і для кожного «прослуховує» випадкову половину каталогу:

| Смак (теги, що подобаються, мінус ті, що ні, ± шум 0.5) | Поведінка |
|---|---|
| ≥ 2 | дослухано; лайк (60 %), у плейлист (30 %) |
| 1…2 | дослухано або 50–90 % |
| 0…1 | 20–60 % (пауза або пропуск після 30 с) |
| < 0 | пропуск у перші 3–20 с |

Події плеєра йдуть через `POST /events` з часом у минулому (останні 20 год), лайки й плейлисти — звичайними ендпоінтами. Друга половина каталогу — відкладена для оцінки. Результат прогону (id користувачів, почуті пісні, теги) — `data/run-<id>.json` (не в git).

## 2. Офлайн-оцінка — `npm run evaluate`

[`src/evaluate.ts`](src/evaluate.ts) чекає, доки Analytics перерахує профілі всіх користувачів прогону, і для кожного питає Recommendations з різними вагами (параметр `weights=content,collaborative,popularity` внутрішнього API): гібрид 0.6/0.3/0.1, лише content, лише collaborative, популярність (бейзлайн), плюс випадковий порядок (бейзлайн).

Релевантні — відкладені пісні, до яких персона має смак ≥ 2 (без шуму). Метрики за користувачем, усереднені: hit rate@k (є хоч одна релевантна в топ-k), precision@k, recall@k для k = 5, 10, і precision@10 за персонами. Звіт — `results/offline-<run>.md`.

## 3. Навантаження — `experiments/k6/run.sh`

k6 з Docker-образу в мережі compose ([`k6/`](k6)):

- `post-song.js` — латентність `POST /song` (5 VU, 30 с);
- `events.js` — пропускна здатність `POST /events` (20 користувачів у межах ліміту 30 запитів/хв, батчі по 20, 60 с) і скільки Analytics потім розбирає чергу;
- `feed.js` — `GET /song/recommended` з Recommendations і з поставленим на паузу Recommendations (фолбек на популярне за таймаутом 800 мс).

Підсумки k6 — `results/k6-<stamp>-*.json`, звіт — `results/load-<stamp>.md` ([`src/k6-report.ts`](src/k6-report.ts)).

## Результати

[`results/`](results) — звіти прогону, на якому написано висновки:

- офлайн: гібрид P@10 35.7 % проти 17.3 % у популярності й 14 % у випадкового; HR@5 = 100 %;
- `POST /song`: медіана 19 мс, p95 49 мс (було ≈ 1.02 с з фейковою транскрипцією 1 с);
- `POST /events`: ≈ 181 подія/с без помилок, Analytics встигає;
- Recommendations недоступний: стрічка відповідає за ≈ 840 мс (таймаут) популярним, 0 помилок.

Тести метрик: `npm test` (вбудований `node --test`).
